# MFIC: Mechanically-Falsifiable Independent Control

The principle behind how this repo verifies its own work. Adapted from workspace3's
`documentation/MFIC.md` (original source:
<https://gist.github.com/pmarreck/b30aa3ca69cb70a5526f8a63ab8c8d7e>).

This is the *why*. The operational rules live in [`AGENTS.md`](../AGENTS.md) § "Checks must
be able to fail" and [`frontend/AGENTS.md`](../frontend/AGENTS.md) § Tests.

## The problem it solves

In this project, agents write the code, the tests and the reviews. A wrong assumption made
while writing the code gets repeated in the test and again in the review, so all three agree
and the suite is green while the behaviour is wrong. That's built into checking your own
work, not a lapse of care. The fix isn't "try harder". It's moving the verdict away from
the author.

## The four properties

A check is only as strong as its weakest property. All four must hold:

| Property | Meaning |
|---|---|
| **Mechanical** | The cases are generated by a machine, not hand-picked by the author. Hand-picked cases encode the author's assumptions, wrong ones included. |
| **Falsifiable** | The check actually fails when the work is wrong. A check that can't fail is vacuous, and a vacuous check is worse than none because it reads as green. |
| **Independent** | The verdict comes from a contract, a real system or a reference, not from the author's claim. "My tests pass" is the author grading their own work. |
| **Control** | The check can reject or block, not just advise. An advisory signal can be waved through. |

## The grounding ladder

What a check's verdict is anchored to, strongest first. Aim as high as the behaviour allows:

1. **A real system.** Compare against the real thing on the same input (a differential oracle).
2. **A contract or invariant.** A property that must hold for every input (metamorphic and
   property-based tests).
3. **Self-consistency.** Round-trips and golden snapshots. They prove the output is
   *unchanged* or *preserved*, not that it is *correct*. A symmetrically wrong pair still
   round-trips clean.
4. **A value the author picked.** The weakest. Fine as a readable example, but not as the gate.

## Independence: what counts and what doesn't

Strongest first:

1. **An oracle.** The verdict comes from a contract, an inverse or a real system, so it doesn't
   matter who wrote the code.
2. **A spec-blind check.** The checker derives its cases from a written specification and
   never sees the code or the author's tests. It can't inherit a blind spot it was never shown.
3. **A different model.** Reduces correlated blind spots, but isn't independence on its own.
4. **Persona prompting is NOT independence.** Asking the same model to "act as a strict
   reviewer" of work it just produced shares the blind spot. It feels like a second opinion
   and isn't one.

## How this repo applies it

| Property | Mechanism | Where |
|---|---|---|
| Mechanical | Hypothesis generates themes and values; metamorphic tests relate two validator runs instead of comparing against hand-picked answers | `frontend/tests/test_properties.py` |
| Falsifiable | Mutation testing (mutmut) with a ratcheted score; each gate is tested to fail on a planted defect and pass a clean file; new tests are red-confirmed by breaking the code | `frontend/run mutate`, `frontend/tests/test_gates.py`, `frontend/.quality_baseline.json` |
| Independent | The theme grammar is extracted from Batocera's own C++ source, never hand-copied | `frontend/src/n64mini/theme_schema/extract.py`, `frontend/vendor/` |
| Independent | Every rule is a numbered requirement grounded in a verbatim engine string (gated against upstream drift) or an explicit project rule | [`requirements/validator.md`](requirements/validator.md), `frontend/tests/test_requirements.py` |
| Independent | A spec-blind agent writes black-box tests from the requirements and engine source, never seeing the implementation; disagreements go to a human | [`.claude/agents/blind-approver.md`](../.claude/agents/blind-approver.md), `frontend/tests/blind/` |
| Control | The pre-commit hook and CI block on `frontend/run check`; the ratchets fail on any regression | `.githooks/pre-commit`, `.github/workflows/` |

## Known gaps

- **Independence is the weak property.** The grammar comes from the engine, but the validator's
  *behaviour* is our reading of that C++, and the golden hashes are snapshots of our own output
  (self-consistency at best).
- **The planned fix is a real-system oracle.** Run the real EmulationStation (RetroBat build,
  `test_harness/live/`) on our themes, including Hypothesis-generated ones, and compare its
  `es_log.txt` warnings with the validator's codes. The engine only reports a subset, so they
  must agree exactly on that subset:

  | Engine log line | Validator code |
  |---|---|
  | `Unknown element of type "X"!` | E030 |
  | `Unknown property : elem.prop` | E031 |
  | `missing "name" attribute!` | E020 |
  | `Included file "…" not found!` | E010 |

  Status: set up, but not yet run (executing the downloaded binary needs approval).
- **The spec-blind check covers the validator only.** The theme's own behaviours (carousel,
  suspend points, Showcase/Full and Original/Port toggles) still need a requirements file before
  the blind approver can check them.
- **The blind approver is the same model family** that wrote the code. It breaks the author's
  framing (it never sees the implementation), not the model's own blind spots. Its blindness is
  enforced by instructions, not technically.

## The cautionary example

The first visual harness (Antigravity, 2026-11-04) scored the theme at 99.97% against the
golden reference. The tiles and box art were cropped *from that same reference*, so the
check could not fail: neither Falsifiable nor Independent. A score is only meaningful
against an input the author didn't derive from the thing being scored.
